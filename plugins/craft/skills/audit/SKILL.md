# craft:audit

Load the `craft:rules` skill first, and follow it where this skill does not say otherwise. Then load `craft:bstack` with the Skill tool, before any pstack skill.

The audit judges the craft process (`docs/adr/0010`). Each rubric asks whether one phase did its job, such as whether the review read the changed files in context. The audit may read code, such as a PR's diff, as evidence of what a phase saw or missed. Every finding points at craft: a phase, skill, step, hook, or rubric to change. The audit never proposes a fix to a project's code, and it never scores the code on its own: it is not a code review.

## Input

No ticket. The owner, or the weekly scheduled task, says "Run craft:audit", optionally with `rubric=<name>`. The session holds the repositories of the projects, the Linear connector, and read access to the bucket `gs://craft-transcripts`.

## Outside the ticket flow

The audit has no ticket, no gate, and no step comment. It makes no branch, commits nothing, and pushes nothing. It writes its scores and findings only into the audit report in Linear (`docs/adr/0009`): never into a repository, a PR, a GitHub comment, or a project file. Its only chat message is the audit message at the end.

**Today** is the date in Europe/Madrid when the audit starts, as `yyyy-mm-dd`. Times in the report are UTC, in ISO 8601.

An **audited ticket** is a craft ticket whose PR merged in the audit window: a PR merged into the project's `Base branch` from its `.claude/craft.md`, whose title starts with `[CRAFT-<n>]`. Other PRs are not audited. Each rubric judges each audited ticket at most once.

Keep the working files of the audit in a scratch directory outside every repository, such as one from `mktemp -d`. `<audit>` below is this skill's directory.

## Rubric file

A rubric is a Markdown file in `<audit>/rubrics/`, a phase rubric, or in `<audit>/rubrics/custom/`, a custom rubric that the owner adds. Its name is the file name without `.md`, such as `review`. A file whose name starts with `_`, such as `rubrics/custom/_example.md`, is a template: the audit skips it. A change to a rubric gets a new rubric version, and the audit compares scores only within one rubric version.

A rubric file has, in this order:

- `# <Name> rubric`, such as `# Review rubric`.
- `Rubric version: <n>`, a whole number.
- `Phase: <phase>`, the craft phase it judges, such as `review`, or `Phase: custom` for a custom rubric.
- Optionally `Applies to: tickets with a spec`. Such a rubric judges only audited tickets whose Linear description has a `## Spec`. It lists the other audited tickets as "not in this phase", and they count in none of its scores. Without the line, the rubric judges every audited ticket.
- `## Items`, with one `### <item name>` heading per item. Each item has the lines `Kind:` (Measure, Check, or Escape), `Reads:` (where its data comes from), and `Score:` (how it is scored).
  - A **Check** also has `Pass:`, `Partial:`, and `Fail:` lines. With the line `Per: craft version`, it is judged once per craft version instead of per ticket.
  - A **Measure** names its script in `Score:`, such as `scripts/rounds.py`, and the values that the script prints.
  - An **Escape** item counts the escapes that the audit traces to the rubric's phase, per searched ticket and craft version, as step 11 says. A rubric has at most one Escape item. A custom rubric has no Escape item, because an escape traces to a phase, not to a custom rubric.

`python3 <audit>/scripts/rubric.py check <file>` checks that a file follows this format.

## Steps

1. **Rubrics.** With no argument, the audit judges every rubric that `python3 <audit>/scripts/rubric.py names` prints: each file in `rubrics/` and `rubrics/custom/` whose name does not start with `_`. With `rubric=<name>`, it judges only that rubric: `python3 <audit>/scripts/rubric.py find <name>` looks in `rubrics/` first, then in `rubrics/custom/`. An unknown name stops the audit: tell the owner in chat that the rubric is unknown, with the list of rubric names that `find` prints, and write no report. Check each rubric with `rubric.py check`; a rubric that fails stops the audit the same way, with its error.
2. **Previous report.** List the Linear documents of the Craft Linear project whose title is `Audit: <yyyy-mm-dd>`. The previous report is the latest audit report from a day before today. Today's own report is never the previous report: `Audit: <today>`, from an earlier run today, is not read. Read the listed tickets of every audit report from before today, from its `## Tickets` section, or from `## PRs` in a report in the CRAFT-85 format, such as `Audit: 2026-11-23`. The fill-up in step 5 leaves out each ticket that any of them lists. With no report from before today, there is no previous report.
3. **Audit window.** It starts at the end of the previous report's window, from the `Window: <start> to <end>` line in its `## Tickets`, or in its `## PRs` in the CRAFT-85 format. With no previous report, it starts 7 days before the audit starts. It ends when the audit starts.
4. **Projects.** The projects are the Linear projects of the `CRAFT` team. The project name is the Linear project's name, such as `Craft Console`. Match each one to the repository in the session that names it as `Linear project` in its `.claude/craft.md`. The Craft Linear project matches `vanoostrum/craft`. A repository or a bucket folder is not a source of projects: a repository that names no Linear project of the team is not audited.

   A project is readable when it has a matched repository and the session can read it on GitHub (`gh api repos/<owner>/<repo>`). Each project that is not readable gets a "skipped" row in `## Tickets` with its reason: "repo not in the environment" when no repository in the session names this Linear project, or "repo cannot be read" when the matched repository fails on GitHub. A project with a readable repository and no bucket folder, such as LibRag, is still audited: its tickets get "no transcripts". If the bucket cannot be read, go on: every ticket gets "no transcripts", and `## Summary` says that the bucket was not read.
5. **Audited tickets.** For each readable project, read `Base branch` in its `.claude/craft.md` on the default branch. List its closed PRs into that branch with `gh api "repos/<repo>/pulls?state=closed&base=<base>&sort=updated&direction=desc&per_page=100&page=<n>"`, page by page, and keep each PR whose title starts with `[CRAFT-<n>]` and whose `merged_at` is in the audit window. A PR merged in the window was updated in it too, so stop at the first PR whose `updated_at` is before the window start. The ticket is the `CRAFT-<n>` in the title; read its Linear description.

   For each rubric that runs, a ticket is judged unless the rubric has `Applies to: tickets with a spec` and the ticket's description has no `## Spec`, such as a plan ticket like `[CRAFT-89] Plan: …`. Then the rubric lists it as "not in this phase". The limits below count only tickets that at least one rubric that runs judges. A ticket that every rubric lists as "not in this phase" is listed in `## Tickets` and counts toward neither limit.
   - **Fill-up.** When the window holds fewer than 5 tickets to judge, over all projects together, add the latest audited tickets merged before the window that no audit report from before today lists, newest first over all projects, until there are 5 to judge or none are left. For the fill-up, keep paging until there are 5 to judge or no page is left, because an older merged PR can have any `updated_at`.
   - **Cap.** When there are more than 40 tickets to judge, take 40, spread evenly over the projects, newest first: take the newest ticket of each project in turn until 40 are taken. Each ticket left out is listed as "skipped" with the reason "over the cap of 40".

   For escapes, keep paging further back, until the first PR whose `updated_at` is before 14 days before the window start. A PR's `updated_at` is never before its `merged_at`, so this finds every PR merged from then to the window end. Keep every merged PR in that span, with any title, and fetch each one's changed paths with `gh api "repos/<repo>/pulls/<n>/files?per_page=100"`, page by page. Write them to `prs.json` in the project's scratch folder: one entry per PR with `number`, `title`, `merged_at`, and `files`, the list of changed paths.
6. **Craft version.** Read the `metadata.json` of each session in the project's bucket folder, `gs://craft-transcripts/<owner>/<repo>/sessions/<id>/metadata.json`. A rubric's segments for a ticket are the segments whose `ticket` is the ticket and whose `step` is the rubric's phase: `review` for the Review rubric, `build` for the Build rubric. A custom rubric (`Phase: custom`) uses the review segments, as the Review rubric does. Per rubric, the craft version of the ticket is the `craft_version` of the latest of its segments, by `started_at`. With no such segment, take the release tags `v<version>` of `vanoostrum/craft`: the release time of a tag is the committer time of the commit it points to. The craft version is the version with the latest release time before the PR's `merged_at`, and the ticket is marked "no transcripts" for that rubric.
7. **Digests.** Each rubric gets the digest of its phase: the full review for `Phase: review` and for custom rubrics, and the build digest for `Phase: build`. Download each transcript to the scratch directory, and run `python3 <audit>/scripts/digest.py` on it. A digest holds the assistant text, each tool call with its input cut at 500 characters, and each tool result cut at 300 characters, or at the cap of `--result-cap <n>`. A cut result keeps the head and the tail, each half of the cap, so the summary line of a test run stays in. The judge reads the digest, never the raw transcript.
   - **Full review.** The first review of the PR; follow-up reviews count only in measures. Its transcript is the first subagent, by `started_at`, of the earliest review segment whose `role` contains "review", case-insensitive: `sessions/<id>/subagents/agent-<agent_id>.jsonl.gz`. With no such subagent, it is the segment's own part of the session transcript: `python3 <audit>/scripts/digest.py sessions/<id>/session.jsonl.gz <started_at> <ended_at>` of the segment.
   - **Build digest.** It covers every build segment of the ticket, retries and fixes after a review FAIL too. A build runs in the session's own transcript, so each segment's part is `python3 <audit>/scripts/digest.py sessions/<id>/session.jsonl.gz <started_at> <ended_at>` of the segment, with the default cap of 300. Each subagent of a build segment, such as verify, the app driver, or CI polling, adds the digest of its own transcript `sessions/<id>/subagents/agent-<agent_id>.jsonl.gz`, with `--result-cap 2000`, so that the verify and app driver output stays readable. The build digest holds all of these in `started_at` order, each after a line `== <role> <started_at> ==`, with the segment's `step` as the role of a segment's own part.

   A ticket with no segment of the rubric's phase, such as a LibRag ticket or a session from before craft recorded segments, has no digest for that rubric. Its checks that read a digest are "no data", not fail: each check whose `Reads:` line names the transcript digest or the build digest, also when it reads a PR comment too, such as Design and maintainability or App evidence. Its checks that read only GitHub or Linear, such as Criteria evidence or Tests check behavior, and its measures are still scored.
8. **Measures.** Run each Measure of each rubric that judges the ticket, with the script that its `Score:` line names and the inputs that its `Reads:` line names: `rounds.py` for Review, `build.py` for Build.
   - **Findings rounds** (Review): save the PR's issue comments with `gh api "repos/<repo>/issues/<n>/comments?per_page=100"` to `comments.json`, and run `python3 <audit>/scripts/rounds.py comments.json`. It prints the status and the values: `PASS`, `no PASS` for a PR that merged without a PASS, such as an escalated merge, or `no data` for a PR with no verdict line, such as a review from before craft 2.9.0. Keep its `values` for `audit.json`, and its status for the rubric's section.
   - **Attempts** and **Feedback speed** (Build): write `build.json` with the project's `Required CI checks` from its `.claude/craft.md`, the ticket's Linear comments, every check run on each commit of the PR from `gh api "repos/<repo>/commits/<sha>/check-runs?filter=all&per_page=100"` for each SHA of the PR's commit list (without `filter=all`, GitHub returns only the latest run of each check, so a red run that was re-run would be lost), and the ticket's build segments from `metadata.json`, as the usage text of `scripts/build.py` shows. Run `python3 <audit>/scripts/build.py attempts build.json` and `python3 <audit>/scripts/build.py speed build.json`, and keep their `values` for `audit.json`. A `null` value is no data.
9. **Judge.** Start one fresh audit judge per audited ticket and rubric that judges it, one at a time, on the `audit judge` model from `models.md` from `craft:rules`. Give it:
   - the rubric file;
   - the ticket's `## Spec`;
   - the PR title, the PR body, and the list of changed files from `gh api "repos/<repo>/pulls/<n>/files?per_page=100"`;
   - the PR diff, saved to a file with `gh api -H "Accept: application/vnd.github.diff" repos/<repo>/pulls/<n>`, as evidence of what the phase saw or missed;
   - the project's repository at the PR's `merge_commit_sha`, which it may read with `git show <sha>:<path>`, such as a whole changed file or the existing code next to it;
   - the PR's review comments: the issue comments of step 8;
   - the digest of the rubric's phase from step 7, or the line "no transcripts";
   - each extra input that an item of the rubric names in its `Reads:` line, each as its own file:
     - the test-file diff: save the PR's files to `files.json` and run `python3 <audit>/scripts/test_diff.py files.json`. With no test file it prints `no test files changed`, which the judge judges against the spec's **Testing decisions**;
     - the project's `CLAUDE.md` at the PR's `merge_commit_sha`, so that the test seam rule is the one the build ran under;
     - the PR's commit list from `gh api "repos/<repo>/pulls/<n>/commits?per_page=100"`: each commit's SHA, message, and time. The judge may read a commit's change with `gh api repos/<repo>/commits/<sha>`, because a squash merge leaves the PR's own commits out of the repository at `merge_commit_sha`;
     - the titles of the ticket's Linear attachments.

   `Reads:` sets what an item must judge. The judge may still read other code as evidence, such as the diff or the repository.

   The prompt says: "You are an audit judge. Judge how craft's process worked on one ticket, against the rubric. You may read the code, such as the diff, as evidence of what the phase saw or missed. Judge the phase, not the code: do not score the code, and never propose a fix to the project's code. When a result points at a problem, name the craft phase, skill, or rule it comes from. A cut result is never evidence against a match or a red run: compare only the part that the digest keeps. Answer each Check without `Per: craft version` as one line `<item> | <pass, partial, fail, or no data> | <evidence>`, with the evidence you cite: a quote, a tool call, or a comment. Answer `no data` when the data the item reads is missing: a check whose `Reads:` line names a digest is `no data` when there is no transcript, even when it also reads a comment." Keep each line whose item is a per-ticket Check of the rubric and whose result is one of the four. A Check without an answer is "no data", and so is a check that reads a digest of a ticket with no digest, whatever the judge answered.
10. **Process logic.** A Check with `Per: craft version` is judged once per rubric and craft version that the audit has a ticket for, not per ticket. For the Review rubric, it is Process logic on the hooks that gate a review session. For the Build rubric, it is Process logic on the hooks that gate a build session and the script `skills/rules/scripts/gallery-shot`. When the previous report's `## Scores` has a row for the same rubric, rubric version, craft version, and item, copy its value and do not judge again. With another rubric version, judge again. Otherwise start one more fresh audit judge on the `audit judge` model, with the rubric file and the files that the item's `Reads:` line names, at the release tag `v<version>` of `vanoostrum/craft`, from `git show v<version>:<path>`. A file that does not exist at that tag, such as `hooks/one_step_per_session.py` before `v2.8.1` or `skills/rules/findings.md` before `v2.9.0`, is left out of the judge's input, and the judge judges the files that exist. The judge may read any other file at that tag with `git show v<version>:<path>` as evidence, such as `hooks/hooks.json`, which decides whether a hook runs at all, or the hook tests. It judges only the files that `Reads:` names. When none of the hooks or scripts that the item names exist at that tag, the result is "no data", with no judge. The judge answers `<item> | <pass, partial, fail, or no data> | <evidence>`.
11. **Escapes.** An escape is a problem in a ticket's work that a craft phase should have caught: a later fix PR, or the owner's feedback at a gate. The audit finds the escapes of the tickets around its window, and an audit judge traces each one to the one phase that should have caught it: `plan`, `spec`, `build`, or `review`. Phase `spec` includes the spec review and `craft:design`, and phase `review` is `craft:review`. The audit may read code as evidence, but it proposes fixes only to craft (`docs/adr/0010`).
    - **Searched tickets.** The audit searches two sets of tickets:
      - every audited ticket that `## Tickets` lists as "audited" or "not in this phase", for fix PRs and for gate feedback;
      - every PR in `prs.json` whose title starts with `[CRAFT-<n>]` and whose `merged_at` is in the 14 days before the window start, for fix PRs only. These are **look-back tickets**. `## Tickets` lists them with the status "look-back". They count toward no limit and get no check.

      Each searched ticket is searched once. An audited or "not in this phase" ticket is not also a look-back ticket, and a ticket with more than one PR, such as a fix after its merge, is one searched ticket: every PR of the ticket goes into `searched.txt`, and its fix PR candidates are those of all its PRs. Its PR is its latest PR. A ticket skipped over the cap is not searched.
    - **Count each escape once.** A fix PR escape counts in the audit whose window holds the fix PR's `merged_at`. A gate feedback escape counts in the audit whose `## Tickets` lists the ticket as "audited" or "not in this phase". The fill-up never takes a ticket that an earlier report lists, so each escape counts once, with no stored state. A fix PR candidate merges at most 14 days after its ticket, so the look-back of 14 days finds every pair.
    - **Fix PR candidates.** Per project, write the PR numbers of its searched tickets to `searched.txt`, one per line, and run `python3 <audit>/scripts/escapes.py candidates prs.json searched.txt <window start> <window end>`. A fix PR candidate is a PR that merged into the same `Base branch` in the window, after the ticket's PR and at most 14 days after it, changes a file that the ticket's PR changed, and is not the ticket's own PR. Any title counts, also a fix that the owner made by hand (`docs/adr/0002`). The script prints one line per candidate: `<ticket PR> <candidate PR> <shared paths>`.
    - **Gate feedback.** For each audited or "not in this phase" ticket, save its Linear comments (`createdAt` and `body`) to `linear.json` and the PR's issue comments of step 8 to `comments.json`, and run `python3 <audit>/scripts/escapes.py gates linear.json comments.json <merged_at>`, with `<merged_at>` the PR's merge time. A gate span runs from a `🤖 Gate: <gate>` comment, or an old `🤖 Pass: <gate>`, to the next `🤖 Approved: <gate>`, the next gate comment for the same gate, or `<merged_at>`. The script prints each span with feedback: owner comments that are not only "approve", `🤖 fix:` comments, and PR comments in the span. Feedback in chat shows through the fix summary that follows it (`findings.md`).
    - **Craft version of an escape.** An escape counts under the ticket's craft version in the escape's phase: the `craft_version` of the ticket's latest segment with that `step` (`plan`, `spec`, `build`, or `review`), as in step 6. With none, the release before the ticket PR's `merged_at`.
    - **Escape judge.** One fresh audit judge per searched ticket that has a fix PR candidate or a gate span with feedback, one at a time, on the `audit judge` model from `models.md` from `craft:rules`. A ticket with neither needs no judge and has 0 escapes. Give it:
      - the ticket's description, with its `## Spec` when it has one;
      - the ticket's PR title, body, changed file list, and diff;
      - the project's repository at the PR's `merge_commit_sha`;
      - each candidate's title, body, changed file list, and the patch of each shared path. The patches of all candidates together stop at 40,000 characters, and then end with `[… cut at 40000 characters]`;
      - each gate span with feedback, as `escapes.py gates` prints it;
      - the skill text of each phase, from `git show v<version>:plugins/craft/skills/<path>` in `vanoostrum/craft`, at the release tag `v<version>` of the ticket's craft version in that phase:
        - plan: `plan/SKILL.md`;
        - spec: `spec/SKILL.md`, `rules/spec-review.md`, `design/SKILL.md`, and `rules/gallery.md`;
        - build: `build/SKILL.md`;
        - review: `review/SKILL.md` and `rules/findings.md`;
        - and `rules/SKILL.md`, with the gates, at the latest of these tags.

        A file that does not exist at a tag is left out, as in Process logic.

      The judge may read any other code as evidence.

      The prompt says: "You are an audit judge. For one ticket, decide for each fix PR candidate and each item of gate feedback whether it is an escape: a problem in the ticket's work that a craft phase should have caught. Name the one phase whose skill text most directly asks for the check that would have caught it; on a tie, the earlier phase. Read the code as evidence, but judge the phase, not the code, and never propose a fix to the project's code." It answers one line per source: `<source> | escape | <phase> | also missed by: <phases or none> | <why, with evidence>`, or `<source> | not an escape | <owner choice, planned change, or unrelated> | <why>`. A source is a candidate as `<repo>#<n>`, or an item of gate feedback as `<gate> gate: <short quote>`.
    - **Not an escape.** "Planned change": a later ticket changes the behavior on purpose, as its spec says. "Unrelated": the shared file changed for another reason. "Owner choice": the owner changes their mind or adds a new wish at a gate, so no phase should have caught it. The report lists these and counts them nowhere.
    - **Escape trace.** Each answer line is the trace of one source. Only the named phase counts an escape; "also missed by" names the other phases that missed it. One fix PR can be an escape of more than one ticket. A source with no answer is "not judged" and counts nowhere.
    - **With `rubric=<name>`, the audit still searches and traces every escape**, because the window moves. `## Escapes` lists them all. `## Scores` prints the escape row of the rubric that ran and the `No rubric` rows. An escape of a phase whose rubric did not run appears only in `## Escapes`.
12. **Scores.** Write `audit.json` in the scratch directory: the rubrics that ran, by name; each audited ticket with its project, ticket, PR number, and per rubric either `"not in this phase"` or its craft version, check results, and measure values; the per craft version results; and `escapes`: `searched`, one entry per searched ticket with `ticket`, `pr` (its latest PR), `spec` (true when its description has a `## Spec`), and `versions`, its craft version per phase, and `traces`, one entry per source with `ticket`, `source`, `answer` (`escape`, `not an escape`, or `not judged`), `phase` for an escape, and `reason` for the others; as the usage text of `scripts/scores.py` shows. Save the previous report's content to `previous.md`. Run `python3 <audit>/scripts/scores.py audit.json previous.md`, or without `previous.md` when there is no previous report. Its output is the `## Scores` section: one row per rubric, rubric version, craft version, and item, with the Phase score (the share of per-ticket checks passed; the Process logic result is shown next to it, not in it), and the value at the last audit from the previous report of the same rubric version, else a dash. A previous report in the CRAFT-85 format gives dashes. Each phase gets an escape row per craft version: the rate of escapes per searched ticket. The review phase's row is the Review rubric's Blind spots item, and it counts only searched tickets with a `## Spec`. A phase with no Escape item in any rubric file, today `plan`, `spec`, and `build`, gets a row with Rubric `No rubric`, Rubric version `—`, and Item `Escapes: <phase>`.
13. **Report.** Write the audit report as the Linear document `Audit: <today>` in the Craft Linear project, with these sections in this order, also when no ticket was judged:
    - `## Summary`: the rubrics that ran, with their rubric versions (with `rubric=<name>`, say that only that rubric ran); the audit window; the counts of "audited", "not in this phase", "look-back", and "skipped" tickets, and the audited tickets per project; the phase score of each rubric per craft version; and the escape count per phase. With no ticket judged, say "No tickets judged." If the bucket was not read, say so.
    - `## Scores`: the output of `scores.py`, unchanged.
    - A `## <Rubric name>` section per rubric, such as `## Review`: a `### <repo>#<n> (<ticket>): <title>` heading per ticket it judged, where `<title>` is the Linear title of the ticket, with each check's result and evidence, and each measure's values and status; then the line "Not in this phase:" with the tickets it does not judge, each with its title; then the Process logic result per craft version, with its evidence or "copied from <previous report>"; then each Escape item per craft version, such as Blind spots in `## Review`, with its rate and the escapes it counts.
    - `## Escapes`: a table with the columns Ticket, Craft version, Source, Phase, Also missed by, and Why, with one row per escape, then the line "Not escapes:" with each source that the judge did not count, and its reason ("owner choice", "planned change", "unrelated", or "not judged").
    - `## Tickets`: the line `Window: <start> to <end>`, then a table with the columns Repository, PR, Ticket, Title, Craft version, Status, and Note. Title is the Linear title of the ticket. Status is "audited", "not in this phase", "look-back", or "skipped". Note holds "no transcripts" where it applies, and the reason of each skip. A skipped project has a row with `—` as PR.

    If `Audit: <today>` exists already, replace its content and keep the document: never create a second one. Then read the document back, and check that its `## Scores` table has the same rows and cells as the output of `scores.py`, apart from Linear's backslash escapes and separator rows.
14. **Message.** Send one chat message to the owner, and a push notification too where the environment has one. It holds the report link; the phase score of each rubric per craft version, each with its trend, such as `0.50 (last audit 0.75)` or `0.50 (last audit —)`; the escape count per phase; and the counts of "audited", "not in this phase", and "skipped" tickets. When no ticket was judged, say so, and that the report says why. Use the `craft:clear-technical-prose` skill.

## Done when

`Audit: <today>` in the Craft Linear project has its sections, its `## Scores` matches `scores.py`, and the owner has the audit message.
